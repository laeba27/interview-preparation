IntermediateTell me about a bug you caused in production. How did you handle it?

AdvancedTell me about a time you disagreed with a senior or a decision-maker.

At Xellerate, the plan was to speed up a slow part of the API by adding caching. When I profiled it, the real problem was N+1 queries: the code was running one query per item in a list.

I didn't just say "you're wrong". I showed the numbers: the query count per request and where the time was going. I suggested we fix the queries and indexes first, and only add caching if it was still slow.

They agreed to try it. Collapsing the queries into joins and adding composite indexes was part of how we got a 35% faster average response time, without the extra complexity of a cache.

With founders, I'd do the same: bring data, offer options, and if they still decide differently, I commit fully to their decision.

Personalise: adjust the details to match what actually happened, including who you disagreed with.

Interviewers look for: disagreeing with data and respect, and "disagree and commit" when the decision goes the other way.

Part 2 — Core Full-Stack

3. Frontend — React & Next.js

IntermediateHow would you build the author dashboard?

I'd start by asking what authors actually come to do. Probably: check where their book is (editing, cover, printing, live), upload files, see sales and royalties, and get help.

Then I'd build it with Next.js App Router:

  • A layout with a sidebar: My Books, Orders, Royalties, Profile.
  • A book page with a clear status timeline, so authors don't need to email support to ask "where is my book?".
  • Server components to load data close to the database, and client components only where there's interaction, like uploads.
  • TanStack Query for data that changes, like order status.
  • Tailwind for a clean, mobile-friendly UI, since many authors will use their phone.

I'd ship the status view first, because that probably cuts the most support tickets.

Interviewers look for: starting from user needs, then structure, then tech. Mentioning reduced support load shows business sense.

IntermediateHow do you manage state in a React app?

I split state into types, because each type has a different best tool:

  • Server data, like an author's books or orders: TanStack Query. It handles caching, loading and refetching, so I don't copy server data into my own state.
  • UI state, like whether a modal is open: plain useState in the component.
  • Form state: React Hook Form.
  • URL state, like filters and the current page: in the query string, so the view can be shared and survives a refresh.
  • Global app state, like the logged-in user or theme: React Context, or Zustand if it grows.

Most apps don't need Redux once server data is handled by TanStack Query.

Interviewers look for: knowing that server state and client state are different problems.

IntermediateWhat's the difference between server and client components in Next.js?

Server components run only on the server. They can read the database or call an API directly, and their code isn't sent to the browser. That means smaller bundles and faster pages.

Client components, marked with "use client", run in the browser too. You need them for anything interactive: useState, click handlers, browser APIs like file uploads.

My default is server components, and I push the client parts down to the smallest piece. For example, a book details page would be a server component, and only the "Upload new cover" button with its progress bar would be a client component.

One thing to be careful about: never pass secrets or sensitive data as props into a client component, because it ends up in the browser.

Interviewers look for: "server by default, client at the leaves", and awareness of what gets sent to the browser.

AdvancedFor public book pages versus the author dashboard, would you use SSR, SSG or ISR?

They have very different needs, so different choices.

Public book pages, with 22,000+ titles: these need to be fast and good for SEO, but they don't change every second. I'd use ISR, which is static generation with revalidation. Pages are built once and cached, then refreshed every so often, or straight away using on-demand revalidation when a book's details change. I wouldn't pre-build all 22,000 at deploy time. I'd build popular ones and let the rest generate on first visit.

Author dashboard: it's private, needs login, and shows personal, changing data like orders and royalties. SEO doesn't matter here. I'd render it dynamically per request, or render the shell on the server and fetch the live parts on the client. It must never be cached publicly.

Interviewers look for: matching the rendering strategy to SEO, freshness and privacy, and knowing not to build 22,000 pages at deploy time.

IntermediateTell me about how you improved load performance by 94%.

At RDX, one of our client apps was loading slowly. First I measured with Lighthouse and the browser Network tab, to see what was actually heavy.

Three things made the difference:

  • Images: they were large PNGs and JPEGs. I converted them to WebP, which is much smaller for the same quality.
  • Lazy loading: images and sections below the fold only loaded when the user scrolled to them.
  • Code-splitting: instead of one big JavaScript bundle, each page and heavy component loaded only when it was needed.

Together that cut load time by 94%. For BookLeaf, book covers are exactly the same problem: a catalogue page with lots of covers would benefit from WebP, proper sizes, and lazy loading.

Personalise: know your before and after numbers (for example, seconds or MB) and which metric the 94% refers to. Interviewers often ask.

Interviewers look for: measure first, then fix, then measure again.

IntermediateHow would you build a manuscript submission form with validation?

I'd use React Hook Form with a Zod schema. The form would have things like title, author name, genre, language, page size, the manuscript file and the cover file.

Validation on the frontend would check:

  • Required fields are filled and lengths are sensible.
  • The file type is allowed, like PDF or DOCX, and the size is under the limit.
  • Clear error messages next to each field, not one big error at the top.

But frontend checks are only for a good experience. The server must validate everything again, using the same Zod schema if possible, because anyone can bypass the browser.

For a long form, I'd also save a draft, so an author doesn't lose everything if they close the tab.

Interviewers look for: a schema-based approach, good error UX, and saying "validate again on the server".

AdvancedHow would you handle large manuscript uploads with a progress bar?

I wouldn't send big files through our own server. At Smile Returns, I built uploads where the browser uploads directly to storage using a signed URL, and I'd do the same here.

  1. The frontend asks our API for an upload URL. The API checks the author is logged in and owns that book.
  2. The API returns a short-lived signed URL for S3.
  3. The browser uploads the file directly to S3. I'd use XMLHttpRequest or Axios with onUploadProgress to show a progress bar, because plain fetch doesn't give upload progress easily.
  4. When it's done, the frontend tells the API, and the API saves the file record.

For very large files, S3 multipart upload lets us retry just the failed part, which helps on slow connections.

Interviewers look for: direct-to-storage uploads, real progress, and handling failures and retries.

IntermediateHow do you use TanStack Query for data fetching and caching?

TanStack Query manages server data for me: loading states, errors, caching and refetching.

For example, an author's order list would use useQuery with a key like ['orders', authorId]. If they leave the page and come back, it shows the cached data instantly and refreshes in the background.

When they do something, like update their book details, I use useMutation. After it succeeds, I invalidate the related query so the list refreshes. For small, safe updates I can do an optimistic update, so the UI changes instantly and rolls back if the server says no.

I also set a sensible staleTime. Royalty reports don't need to refetch every second, but order status can refresh more often.

Interviewers look for: query keys, invalidation after mutations, and choosing staleness based on the data.

BasicHow do you make a web app accessible?

I start with the basics, because they cover most problems:

  • Use proper HTML elements, like <button> for buttons and <label> for inputs, not clickable divs.
  • Every image has useful alt text, for example a book cover's alt is the book title.
  • Everything works with the keyboard, and focus is visible.
  • Enough colour contrast, and never use colour alone to show status, like "red means failed".
  • Form errors are linked to their fields so screen readers announce them.

I check with Lighthouse and by tabbing through the page myself. React Testing Library also nudges you towards accessible code, because you find elements by role and label.

Interviewers look for: practical habits over a list of ARIA attributes. Semantic HTML first.

BasicHow do you approach responsive design?

I design mobile-first. With Tailwind, I write the mobile styles by default and add breakpoints like md: and lg: for bigger screens.

For an author dashboard, that means things like: the sidebar becomes a menu on mobile, tables of orders turn into stacked cards, and buttons are big enough to tap.

I use flexbox and grid instead of fixed widths, and I test on real phone sizes in Chrome DevTools, and on an actual phone before release.

A lot of Indian authors will check their book status on their phone, so I'd treat mobile as a first-class experience, not an afterthought.

Interviewers look for: mobile-first thinking and concrete patterns, like tables becoming cards.

IntermediateWhat are error boundaries and how do you handle errors on the frontend?

An error boundary catches errors while rendering a part of the page, so one broken widget doesn't crash the whole app. In Next.js App Router, I can add an error.tsx file to a route, and it shows a fallback with a "Try again" button.

So if the royalties chart fails, the author still sees their books and orders. Only that section shows an error.

Error boundaries don't catch everything, like errors in event handlers or failed API calls. For those, I handle the error state in TanStack Query and show a friendly message.

And I'd log errors to something like Sentry, so we find out about problems before authors email us.

Interviewers look for: knowing what error boundaries do and don't catch, and the habit of logging errors.

IntermediateHow do you handle authentication on the frontend?

The main rule is: the frontend is never the real security. It only improves the experience. The server checks every request.

What I do on the frontend:

  • Store the session in an httpOnly, secure cookie, not localStorage, so JavaScript can't read it if there's an XSS bug.
  • Use Next.js middleware to redirect logged-out users away from dashboard pages before they load.
  • Hide buttons the user's role can't use, like "Approve cover" for authors. But the API still checks the role.
  • Handle an expired session cleanly, by redirecting to login and returning them to where they were.

Interviewers look for: "the server enforces, the client just reflects", plus httpOnly cookies over localStorage.

4. Backend & APIs

BasicHow would you design a REST API for authors, books and orders?

I'd use nouns for resources and HTTP methods for actions:

GET    /authors/:id
GET    /authors/:id/books
POST   /books
GET    /books/:id
PATCH  /books/:id
POST   /books/:id/files       (manuscript, cover)
GET    /orders?status=printing&page=2
POST   /orders
POST   /orders/:id/cancel

A few rules I follow: plural nouns, filters in the query string, PATCH for partial updates, and a consistent error format everywhere. Something like "cancel an order" isn't a simple update, so a small action endpoint is clearer than trying to force it into PATCH.

At Xellerate I built 95+ endpoints, and consistency was what kept them easy to use.

Interviewers look for: resource naming, correct methods, and a sensible answer for actions that aren't plain CRUD.

BasicWhich HTTP status codes do you use most and when?
  • 200 OK, 201 Created (new order), 204 No Content (successful delete).
  • 400 bad input, like a missing title. 422 if the input is well-formed but breaks a rule.
  • 401 not logged in. 403 logged in but not allowed, like an author trying to see another author's royalties.
  • 404 not found. 409 conflict, like a duplicate ISBN.
  • 429 too many requests.
  • 500 our bug. 502/503 an upstream service, like a print API, is down.

The common mistake is returning 200 with {"error": ...} inside. That breaks monitoring and client error handling.

Interviewers look for: the 401 vs 403 difference, and not hiding errors inside a 200.

IntermediateHow do you paginate large lists, like 22,000 titles?

There are two main ways.

Offset pagination: ?page=3&limit=20. It's simple and lets you jump to page 50, so it's fine for admin tables. But on big tables it gets slower the deeper you go, and if new rows are added you can see duplicates.

Cursor pagination: ?after=<last id>&limit=20. The query uses WHERE id > last_id, which uses an index and stays fast. It's best for infinite scroll or feeds, like a public catalogue.

For the ops dashboard I'd probably use offset, and for public browsing or big exports, cursor. Either way I'd set a max limit, so nobody can request 22,000 rows at once.

Interviewers look for: knowing both, the trade-offs, and capping the page size.

IntermediateHow do you version an API?

The simplest and most common way is in the URL: /api/v1/orders. It's easy to see and easy to route.

But I try not to need new versions often. Adding a new field or a new endpoint doesn't break anyone, so that's fine in v1. I only need v2 for breaking changes, like renaming a field or changing what a status means.

When I do create v2, I keep v1 working for a while, tell the people using it, and remove it later.

This matters more when external parties use the API, for example partners or a mobile app. For an internal dashboard where we control both sides, we can usually just change both together.

Interviewers look for: knowing what counts as a breaking change, and a plan for retiring old versions.

AdvancedHow would you handle a payment webhook, for example from Razorpay?

I haven't integrated Razorpay in production yet, but I've read how its webhooks work, and the pattern is the same for most providers.

  1. Verify the signature. Razorpay sends an X-Razorpay-Signature header, an HMAC-SHA256 of the raw body using our webhook secret. I compute it myself and compare. If it doesn't match, I reject it.
  2. Make it idempotent. Webhooks can arrive more than once. I store the event ID, and if I've already processed it, I just return 200.
  3. Respond fast. I save the event and return 200 quickly, then do the heavy work, like confirming the order and sending emails, in a background job.
  4. Don't trust the order of events. I check the current status before updating.

And I'd never mark an order paid just because the frontend said so. The webhook or a server-side check is the source of truth.

Interviewers look for: signature check, idempotency, quick acknowledgement, and honesty about not having used Razorpay yet.

IntermediateHow would you send webhooks to other systems?

Say BookLeaf wants to notify a print partner or an n8n workflow whenever a book is approved for printing.

  • When the event happens, I save it to an events table in the same database transaction. That way, I never lose an event even if the send fails.
  • A background worker sends it as a POST with a JSON body and an event ID.
  • I sign the body with HMAC, so the receiver can check it really came from us.
  • If the receiver fails or times out, I retry with increasing delays, like 1 minute, 5 minutes, 30 minutes, and after a few tries mark it as failed for someone to check.

Because of retries, receivers might get the same event twice, so the event ID lets them ignore duplicates.

Interviewers look for: reliable delivery (store first, then send), signing, retries with backoff, and event IDs.

AdvancedWhat is idempotency and why does it matter?

An operation is idempotent if doing it twice has the same effect as doing it once.

It matters a lot with payments and orders. Imagine an author clicks "Pay" and their internet drops. The browser retries. Without idempotency, we might create two orders or charge them twice.

The fix is an idempotency key. The client sends a unique key with the request. The server stores it with the result. If the same key comes again, the server returns the saved result instead of doing the work again. A unique constraint in the database makes this safe even if two requests arrive at the same moment.

GET, PUT and DELETE should already be idempotent. POST is the one that needs this extra care.

Interviewers look for: a real example like double payment, and using a database constraint, not just an "if exists" check.

AdvancedGenerating a print-ready PDF takes minutes. How would you handle that?

I wouldn't do it inside the API request. It would time out, and the author would sit there waiting.

Instead I'd use a background job queue, like BullMQ on Redis:

  1. The API creates a job, like "generate print PDF for book 123", saves the status as queued, and returns straight away.
  2. A separate worker process picks up the job, generates the PDF, uploads it to S3, and sets the status to ready.
  3. The dashboard shows the status, by polling or a notification.

Jobs get retries with backoff, and if one keeps failing, it moves to a failed list and alerts someone. I'd also limit how many run at once, because PDF generation is heavy. With 1,200 books a month, you don't want ten big jobs starving the server.

Interviewers look for: moving slow work off the request, status tracking, retries, and concurrency limits.

IntermediateHow would you store manuscripts and cover files?

Files go in object storage like S3, not in the database and not on the app server's disk. The database only stores the file's key, type, size, owner and version.

At Smile Returns, I built access-controlled storage with time-limited signed URLs, and I'd use the same idea here:

  • The bucket is private. No public links.
  • When an author or editor needs a file, the API checks they're allowed and gives a signed URL that expires in a few minutes.
  • Uploads go directly from the browser to S3, so our server doesn't carry big files.

I'd also keep versions, because manuscripts get revised many times, and you want to know exactly which file went to print.

Interviewers look for: private storage, signed URLs, metadata in the DB, and versioning.

IntermediateHow would you implement rate limiting?

Rate limiting stops abuse, like someone trying thousands of passwords, or a buggy script hammering the API.

I'd use Redis to count requests per user or IP in a time window. For example, login allows 5 attempts per minute per IP and email, while normal API calls allow a much higher limit. When the limit is hit, I return 429 with a Retry-After header.

Redis matters because if we run more than one server, they all share the same counter.

The strictest limits go on sensitive or expensive endpoints: login, OTP, password reset, and anything that calls OpenAI, because each call costs money.

Nginx can also do basic rate limiting in front of the app.

Interviewers look for: a shared store like Redis, different limits for different endpoints, and the 429 response.

IntermediateHow do you handle validation and errors in a Node API?

Validation: every request body, query and param goes through a Zod schema at the start of the route. Unknown fields are dropped, so nobody can sneak in something like role: "admin".

Errors: I have one central error-handling middleware in Express. Routes throw typed errors, like NotFoundError or ForbiddenError, and the middleware turns them into the right status code and a consistent JSON shape:

{ "error": { "code": "BOOK_NOT_FOUND", "message": "Book not found" } }

For unexpected errors, the user sees a generic message, while the full stack trace goes to our logs with a request ID. We never leak stack traces or SQL errors to the client.

Interviewers look for: validation at the edge, one central error handler, consistent error format, and no leaking internals.

IntermediateNode.js or Python? Which would you choose for BookLeaf's backend?

For the main web backend, I'd lean towards Node.js with TypeScript. The frontend is React and Next.js, so the whole team uses one language, and we can share types and validation schemas. Node is also great for I/O-heavy work like APIs, webhooks and calling third-party services, which is most of what BookLeaf does.

Python is stronger for data work, scripts, and some AI and document-processing libraries. If we needed heavy manuscript analysis or PDF processing that has better Python tools, I'd happily build that as a separate small service or worker.

So my answer: Node for the core, Python where it clearly wins. My own production experience is mostly Node, but I'm comfortable picking up Python.

Interviewers look for: a reasoned choice tied to the team and workload, not "Node is better".

BasicHow do you document APIs?

I like OpenAPI (Swagger) specs, because they give a readable page where people can try the endpoints, and they can generate client types.

If I'm using Zod for validation, I can generate the OpenAPI spec from the same schemas, so the docs don't go out of date.

I also use Postman a lot. With 95+ endpoints at Xellerate, having saved example requests made testing much easier, and a shared collection is a quick way to help the frontend team.

On top of that, a short README covering how to run the project, the environment variables, and how auth works. In a small team where people come and go, that saves a lot of time.

Interviewers look for: docs that stay in sync with code, and thinking about the next developer.

AdvancedHow do you integrate third-party APIs reliably, like print or distribution APIs?

I assume the other service will sometimes be slow, down, or return something odd. So:

  • Timeouts on every call. Without one, a hanging print API can tie up our server.
  • Retries with backoff, but only for safe cases, like timeouts and 5xx errors, and with an idempotency key if it's a create.
  • Background jobs for anything not needed instantly, like sending an order to the printer.
  • One wrapper module per provider, so if the API changes, I fix one file.
  • Logging each request and response, so when a book doesn't reach a distributor, we can see why.
  • Alerts when failures pile up.

And I store our own status in our database, instead of asking the third party every time.

Interviewers look for: timeouts, safe retries, isolation behind a wrapper, and visibility when things fail.

5. Databases & Performance

BasicSQL or NoSQL for BookLeaf's core data?

SQL, specifically PostgreSQL, for the core.

BookLeaf's data is very connected: authors have books, books have orders, orders have payments, and royalties depend on all of them. That's exactly what relational databases are good at. You get joins, foreign keys so you can't have an order for a book that doesn't exist, and transactions, which you really want when money is involved.

NoSQL still has a place. Redis for caching, sessions, rate limits and job queues. And Postgres has JSONB columns, so for flexible data, like extra metadata from different distribution platforms, I can store it as JSON without a separate database.

I've used PostgreSQL, MySQL and MongoDB, and for this kind of business I'd pick Postgres.

Interviewers look for: a choice driven by the data's shape and the need for transactions, not by trend.

IntermediateSketch a schema for authors, books, orders and royalties. 
authors      (id, name, email, phone, country, created_at)
books        (id, author_id → authors, title, isbn UNIQUE,
              status, package_id, created_at)
book_files   (id, book_id → books, kind [manuscript|cover|print_pdf],
              storage_key, version, uploaded_by, created_at)
orders       (id, book_id → books, channel [website|amazon|...],
              quantity, unit_price, currency, status, created_at)
payments     (id, order_id → orders, provider, provider_payment_id UNIQUE,
              amount, status, created_at)
royalties    (id, author_id → authors, book_id → books, order_id → orders,
              amount, currency, period, status [pending|paid])

Some choices I'd point out: money stored as integers in paise or cents, never floats. Currency stored on each row, because BookLeaf sells in India and the US. Royalties as their own rows, linked to the order, so every rupee paid to an author can be traced back to a sale. And unique constraints on ISBN and provider payment ID to stop duplicates.

Interviewers look for: sensible relationships, money as integers, multi-currency, and an audit trail for royalties.

IntermediateTell me about how you used indexing to improve performance.

At Xellerate AI, I cut the average API response time by 35%. I didn't guess. I profiled the slowest, most-used endpoints first.

Part of it was indexing. Many queries filtered on two columns together, like "matches for this startup with this status". So I added composite indexes on those column pairs, in the right order. The most selective, most-filtered column goes first.

The other part was fixing N+1 queries, which I can explain too.

At Smile Returns, I did something similar for appointment booking lookups, and that was part of a 30% query speed-up.

I'm also careful not to over-index. Each index slows down writes and takes space, so I only add ones that real queries need.

Personalise: remember one specific query and index you added, so you can describe it if asked to go deeper.

Interviewers look for: measure first, composite index column order, and awareness of the write cost.

IntermediateWhat is the N+1 query problem and how do you fix it?

It's when you run one query to get a list, then one more query for each item in the list.

For example, load 50 orders, then for each order run a separate query to get its book title. That's 51 queries instead of one or two. It's easy to miss with an ORM, because the code looks innocent.

The fixes:

  • Use a join, so it's one query.
  • Or load the related rows in one batch with WHERE id IN (...). In Prisma, using include does this.

At Xellerate I collapsed several N+1 patterns into joined selects, and it was a big part of the 35% improvement. To spot them, I log the number of queries per request in development.

Interviewers look for: a clear example, the fix, and how you detect it.

AdvancedHow do you keep a payment and an order consistent?

I use a database transaction, so related changes either all happen or none do.

When a payment is confirmed, in one transaction I:

  1. Insert the payment row, where a unique provider payment ID stops duplicates.
  2. Update the order status to paid, but only if it's currently pending.
  3. Create the royalty entry for the author.

If any step fails, everything rolls back. We never have a paid order with no payment record.

One important point: I never call an external API, like the payment gateway or an email service, inside the transaction. That holds locks while waiting on the network. I commit first, then trigger emails or print jobs in the background.

Interviewers look for: transactions, conditional updates to avoid double processing, and keeping network calls outside the transaction.

IntermediateHow do you run database migrations safely?

I use a migration tool, like Prisma Migrate, so every schema change is a file in Git, reviewed, and run the same way in every environment.

For a live system, I avoid changes that break running code. For example, to rename a column:

  1. Add the new column.
  2. Deploy code that writes to both.
  3. Copy the old data across.
  4. Switch reads to the new column.
  5. Drop the old column later.

I also watch out for migrations that lock big tables, like adding an index on a huge table. In Postgres I'd use CREATE INDEX CONCURRENTLY. And I always take a backup before a risky migration.

Interviewers look for: migrations in version control, the expand-then-contract pattern, and awareness of table locks.

IntermediateWhat is normalization, and when would you denormalize?

Normalization means storing each fact in one place. For example, an author's email lives only in the authors table, not copied into every book and order. That way, when it changes, you update one row and nothing goes out of sync.

At Smile Returns I normalised the prescription and appointment schemas, removing duplicated data, and together with indexing that improved query speed by 30%.

But sometimes you denormalize on purpose. Good examples for BookLeaf:

  • Copy the price onto the order when it's placed. If the book's price changes later, old orders should still show what was actually paid.
  • Keep a running total of sales per book for a fast dashboard, instead of counting every time.

Interviewers look for: understanding both sides, with good reasons to denormalize, like historical accuracy and read speed.

IntermediateHow would you use Redis for caching?

I'd cache data that's read often and changes rarely. For BookLeaf, things like public book details, the catalogue's category lists, or an author's monthly royalty summary.

The usual pattern is cache-aside: check Redis first. If it's there, return it. If not, read from Postgres, save it to Redis with an expiry, and return it.

The hard part is keeping it fresh. When a book's details change, I delete its cache key, so the next read gets the new data. And every key has a TTL as a safety net.

I wouldn't cache things that must be exactly right in real time, like payment status. And I'd only add caching after fixing slow queries, not as a way to hide them.

Interviewers look for: cache-aside, invalidation on write, TTLs, and knowing what not to cache.

AdvancedA page is slow. How do you find the slow query?
  1. Find which request is slow, using logs or APM timings per endpoint.
  2. Find which queries it runs and how long each takes. In Postgres, pg_stat_statements shows the slowest and most-called queries.
  3. Run EXPLAIN ANALYZE on the slow query. It shows the real plan and timing.

Things I look for in the plan:

  • A Seq Scan on a big table where I expected an index.
  • Estimated rows very different from actual rows, which means stale statistics, so I run ANALYZE.
  • Sorting on a column with no index.

Then I fix it, with an index, a rewritten query, or fewer columns, and run EXPLAIN ANALYZE again to confirm. That's the same measure-fix-measure approach I used at Xellerate.

Interviewers look for: a methodical process and being able to read basic plan output.

IntermediateHow would you handle database backups?

A backup you've never restored is just a hope. So:

  • Automatic daily backups, plus point-in-time recovery if we're on managed Postgres like AWS RDS. That lets us restore to just before a mistake, like someone deleting the wrong rows.
  • Backups stored in a different place from the main database.
  • Test restores regularly, for example once a month, into a separate database, to make sure they actually work.
  • Manuscripts and covers in S3 with versioning turned on, so a deleted or overwritten file can be recovered.

For a business with 22,000 titles and authors' royalty history, losing data would be a disaster, so this is worth getting right early.

Interviewers look for: automated backups, point-in-time recovery, and actually testing restores.

AdvancedHow do you make sure one author can never see another author's data?

I use two layers.

In the application: every query for author data is filtered by the logged-in author's ID, which comes from the session, never from the request body. So it's WHERE author_id = :currentAuthor, always. I put that in a shared helper, so nobody forgets it.

In the database: PostgreSQL row-level security. At Xellerate, I set up RLS policies so the database itself only returns rows the current user is allowed to see. Even if a developer forgets the filter in some new endpoint, the database blocks it.

I'd also write tests that log in as author A and try to read author B's book, expecting a 403 or 404. At Smile Returns, the multi-tenant healthcare platform had the same need to keep each tenant's data separate.

Interviewers look for: defence in depth, IDs from the session, and tests for cross-user access.

IntermediateHow would you build search across 22,000+ titles?

22,000 rows is not huge, so I'd start with Postgres itself before adding a new tool.

  • Full-text search with a tsvector column on title, author name and description, and a GIN index. That handles word matching and ranking.
  • Typo tolerance with the pg_trgm extension, so "harry poter" still finds results.
  • Filters like genre and language as normal indexed columns.

I'd debounce the search box on the frontend, so we don't send a request on every keystroke, and paginate the results.

If we later need advanced features, like instant search-as-you-type or very fuzzy matching across millions of rows, I'd consider Meilisearch or Elasticsearch. But I wouldn't add that complexity on day one.

Interviewers look for: right-sizing the solution, and knowing when to grow into a dedicated search engine.

6. Auth & Security

BasicJWT or sessions? Which would you use?

Sessions: the server stores the session, for example in Redis, and the browser holds a random session ID in a cookie. It's easy to log someone out instantly, because you just delete the session.

JWT: the token itself contains the user info, signed by the server. No lookup is needed, which is handy across many services. But it's hard to revoke before it expires.

For BookLeaf's author dashboard and internal tools, I'd use sessions in an httpOnly, secure cookie. It's simpler and safer, and instant logout matters, for example when an ops staff member leaves.

If we needed tokens, say for a mobile app or service-to-service calls, I'd use short-lived JWTs with refresh tokens. I've used both JWT and session-based auth before.

Interviewers look for: the revocation trade-off and a choice that fits the product.

IntermediateHow would you add "Sign in with Google" for authors?

I'd use OAuth 2.0 with OpenID Connect, using the authorisation code flow with PKCE. In Next.js, a library like Auth.js handles most of this safely.

The flow:

  1. The author clicks "Sign in with Google" and is sent to Google.
  2. Google sends them back with a one-time code.
  3. Our server swaps the code for tokens and verifies the ID token.
  4. We find or create the author by their Google account ID, then create our own session.

One thing to handle carefully: an author who first signed up with email and password and later uses Google with the same email. I'd only link the accounts if Google says the email is verified.

We don't need Google's tokens after login, so I wouldn't store them.

Interviewers look for: knowing the code flow, PKCE, verifying the ID token, and safe account linking.

AdvancedHow would you design roles for admins, ops staff and authors?

I'd use role-based access control, with permissions rather than checking role names everywhere.

  • Author: manage their own books and files, see their own orders and royalties.
  • Ops: see all books, update production status, manage orders. No access to payouts.
  • Finance: royalties and payouts.
  • Admin: everything, including managing staff.

In code, a route checks a permission, like can('royalties:approve'), and roles map to permissions. Adding a new role later is just configuration.

At Xellerate, I built RBAC with access control lists across 10+ roles, and backed it with row-level security in PostgreSQL, so data rules were enforced in the database too, not just the API.

I'd also log sensitive actions, like who approved a royalty payout.

Interviewers look for: permissions over role checks, least privilege, enforcement in more than one layer, and audit logs.

IntermediateWhere would you store API keys and secrets, like an OpenAI key?

Never in the code, never in Git, and never in the frontend.

  • Locally, in a .env file that's in .gitignore.
  • In production, in environment variables or a secrets manager like AWS Secrets Manager, and in GitHub Actions secrets for CI/CD.
  • The OpenAI key is only used on the server. The browser calls our API, and our API calls OpenAI. If the key were in the frontend, anyone could steal it and run up a huge bill.

I'd also set a spending limit on the OpenAI account, use separate keys for development and production, and rotate a key immediately if it ever leaks. I'd add a secret scanner to CI to catch accidental commits.

In Next.js specifically, anything prefixed NEXT_PUBLIC_ goes to the browser, so secrets must never use that prefix.

Interviewers look for: server-only keys, a secrets manager, rotation, and cost limits on paid APIs.

IntermediateExplain SQL injection, XSS and CSRF, and how you prevent them.

SQL injection: user input gets treated as part of a SQL query, so someone can type ' OR 1=1 -- and read data they shouldn't. Fix: always use parameterised queries or an ORM like Prisma. Never build SQL by joining strings.

XSS: someone stores a script, for example in a book description, and it runs in other users' browsers. Fix: React escapes output by default, so avoid dangerouslySetInnerHTML. If we must show rich text, sanitise it with something like DOMPurify. A Content Security Policy adds another layer.

CSRF: another website tricks a logged-in user's browser into sending a request to our site. Fix: SameSite cookies, plus CSRF tokens for forms that change data.

And I keep dependencies updated, since many real attacks come through old packages.

Interviewers look for: a simple explanation of each attack and a concrete fix, not just the definitions.

IntermediateHow would you protect authors' unpublished manuscripts?

An unpublished manuscript is an author's most valuable work, so a leak would really hurt trust.

  • Private S3 bucket. No public URLs, ever.
  • Access only through short-lived signed URLs, given only after checking the person is the author or staff working on that book. I built exactly this at Smile Returns.
  • Encryption at rest, which S3 supports, and HTTPS everywhere.
  • File IDs that can't be guessed, like UUIDs, not manuscript_1.pdf.
  • An access log of who downloaded what and when.
  • Staff access limited to the roles that actually need it.

If we send manuscript text to an AI service, I'd check that provider's data-use terms first, and be open with authors about it.

Interviewers look for: layered protection and awareness that AI integrations also touch author data.

BasicHow should passwords be stored?

Never in plain text, and never with a fast hash like MD5 or SHA-256 alone.

I use a slow password-hashing algorithm, like bcrypt or Argon2. They automatically add a random salt, so two users with the same password get different hashes. And they're deliberately slow, so if the database ever leaks, cracking the passwords takes a very long time.

Alongside that:

  • Rate-limit login attempts.
  • Reset tokens that are random, single-use, and expire quickly.
  • The same error message for "wrong email" and "wrong password", so attackers can't find which emails are registered.

Or, use Google login so we don't store a password at all.

Interviewers look for: bcrypt or Argon2, salting, and why a slow hash matters.

AdvancedHow do you verify a webhook really came from Razorpay or Stripe?

They sign each webhook using a shared secret, and I check that signature.

For Razorpay, the X-Razorpay-Signature header is an HMAC-SHA256 of the request body using our webhook secret:

const expected = crypto
  .createHmac('sha256', process.env.RAZORPAY_WEBHOOK_SECRET)
  .update(rawBody)
  .digest('hex');
const ok = crypto.timingSafeEqual(
  Buffer.from(expected), Buffer.from(signatureHeader));

Important details:

  • Use the raw body. If Express parses the JSON first and I re-stringify it, the signature won't match.
  • Use a timing-safe comparison, and check the lengths match first, because timingSafeEqual throws on different lengths.
  • Stripe also signs a timestamp, so I reject old events to stop replays. Their SDK does this check for me.

I haven't done this with Razorpay in production yet, but I've read the docs, and it's the same HMAC pattern I'd use for signing our own outgoing webhooks.

Interviewers look for: HMAC with a secret, the raw-body gotcha, timing-safe comparison, and replay protection.

IntermediateHow would you handle authors' personal data and privacy?

We hold names, emails, phone numbers, addresses, and bank or tax details for royalties. That's sensitive. India's Digital Personal Data Protection Act, 2023, and similar rules for US customers, mean we must handle it carefully.

  • Collect only what's needed. Don't ask for things we don't use.
  • Limit access. Bank details visible only to finance, not all ops staff.
  • Encrypt the most sensitive fields, like bank account numbers, and mask them in the UI.
  • Keep it out of logs. No full phone numbers or bank details in error logs.
  • Be careful with third parties. Don't send personal data to automation tools or AI services unless it's really needed.
  • Support deletion when an author asks, while keeping the financial records we're legally required to keep.

Interviewers look for: data minimisation, access control, awareness of the DPDP Act, and thinking about third-party tools.

7. AI & LLM Integration

BasicHow would you add an OpenAI feature to our author dashboard?

The main rule is that the browser never talks to OpenAI directly. The dashboard calls our own backend endpoint, and the backend calls OpenAI with the API key stored on the server.

  • The author clicks something like "Suggest a blurb" in the dashboard.
  • Our API checks they are logged in and own that book, then builds the prompt from the book's data.
  • The backend calls the model, validates the response, and saves it as a draft.
  • The author edits and approves it. Nothing goes live without a human.

I'd also log each call with the book ID, model, tokens used and cost, so we can see what it's costing us per book. While we're still on Bubble, the same backend endpoint can be called from Bubble's API Connector, so the work isn't wasted when we migrate.

Interviewers look for: key stays on the server, auth before the AI call, output saved as a draft, and cost logging from day one.

BasicWhere do you think AI can actually help BookLeaf?

I'd look for tasks that are repetitive, text-heavy and happen 1,200 times a month. A few that stand out:

  • Metadata: drafting the back-cover blurb, keywords, and suggesting BISAC or genre categories from the synopsis.
  • Manuscript checks: flagging missing chapters, inconsistent headings, or a missing dedication page before it reaches the formatting team.
  • Cover briefs: turning the author's rough notes into a clear brief for the designer.
  • Support: drafting replies to common questions like "Where is my ISBN?" or "When will I get royalties?" for the team to approve.
  • Ticket triage: tagging incoming emails by type and urgency.

I'd start with the one that saves the ops team the most hours, measure it, and only then expand.

Interviewers look for: ideas tied to the real business, not "add a chatbot", and a plan to start small and measure.

BasicWhat are the basics of writing a good prompt?

I treat a prompt like a brief to a new colleague who knows nothing about us.

  • Role and context: "You write back-cover blurbs for a self-publishing house in India."
  • Clear task and limits: "Write a blurb under 150 words. Don't invent plot points not in the synopsis."
  • Examples: two or three good blurbs we've approved before. This helps a lot with tone.
  • Output format: exactly what fields I want back.
  • Separate data from instructions: put the author's text inside clear tags so it isn't treated as instructions.

I keep prompts in version control, not hard-coded in random places, and I test changes on a fixed set of sample books before shipping. Temperature I keep low for extraction and categorisation, a bit higher for creative blurbs.

Interviewers look for: context, examples, output format, and treating prompts as code that gets versioned and tested.

IntermediateHow do you get reliable JSON out of an LLM?

I don't rely on "please reply in JSON" in the prompt anymore. Both OpenAI and Anthropic now support structured outputs, where I pass a JSON schema and the model's response is constrained to match it. Tool or function calling with a schema works in a similar way.

For example, for book metadata I'd define a schema with title, blurb, keywords as an array, and genre as an enum of our allowed genres.

But I still validate on my side with Zod, because the shape can be right while the content is wrong, like an empty blurb or a genre that doesn't fit. If validation fails, I retry once with the error message added, and if it fails again I mark the task for a human. I never let unvalidated AI output go straight into the database.

Interviewers look for: knowing about structured outputs / JSON schema, plus your own validation and a fallback path.

IntermediateWhat are hallucinations, and how would you guard against them?

A hallucination is when the model says something confidently that isn't true. For us, that could be a blurb that invents a plot twist, or a support reply that promises a royalty date we never committed to.

How I'd reduce it:

  • Give the model the actual facts, like the synopsis or our policy text, and tell it to use only that.
  • Allow it to say "I don't know" instead of guessing.
  • Keep anything with money, dates or legal terms out of AI-generated text, or pull those values from the database, not from the model.
  • Validate outputs with simple checks, like length, banned phrases, or whether a promised date exists.
  • Most importantly, keep a human approving anything an author will see.

Interviewers look for: grounding in real data, letting the model refuse, and human review for anything customer-facing.

BasicHow do you keep AI API keys safe?

Same as any secret. The key only lives on the server, in environment variables or a secrets manager, never in frontend code, never in Git, and never in a Bubble client-side workflow where it could show up in the browser.

  • In Bubble, I'd mark the key as private in the API Connector so it stays server-side.
  • Separate keys for development and production, so a leaked dev key can't burn the production budget.
  • Set usage limits and budget alerts in the OpenAI or Anthropic console.
  • Our own endpoint is behind auth and rate limited, so nobody can use our backend as a free proxy to the model.
  • If a key leaks, rotate it immediately.

Interviewers look for: server-side only, separate keys per environment, spend limits, and rate limiting your own AI endpoint.

IntermediateThe AI provider is slow, rate-limiting you, or down. What do you do?

I design for this from the start, because it will happen.

  • Retries: on a 429 or 5xx error, retry with exponential backoff and a bit of jitter, and respect the Retry-After header. Don't retry on a 400, that's our bug.
  • Timeouts: set a clear timeout so a request doesn't hang forever.
  • Background jobs: for bulk work, like generating metadata for 200 books, put it in a queue and process at a controlled rate instead of firing everything at once.
  • Fallbacks: switch to a second model or provider, or just show "AI suggestions are unavailable right now, you can write it manually".

The key point is that AI is a helper. If it's down, authors should still be able to submit books and the team can still work.

Interviewers look for: backoff, timeouts, queues for bulk work, and graceful degradation so core flows never depend on the AI.

IntermediateHow would you control AI costs?

Cost is basically tokens in plus tokens out, times the model's price. So I'd work on each part:

  • Right model for the job: a small, cheap model for tagging and categorisation, a bigger one only for things like blurbs where quality matters.
  • Send less text: don't send a 300-page manuscript when the synopsis and table of contents are enough.
  • Limit output: set max output tokens.
  • Caching: store results so the same request isn't paid for twice, and use the providers' prompt caching for long, repeated system prompts.
  • Batch API: for non-urgent bulk jobs, both OpenAI and Anthropic offer batch processing at a discount.

And I'd track cost per feature and per book in a simple dashboard, so the founders can see if it's worth it.

Interviewers look for: model choice, trimming input, caching, batch for bulk work, and measuring cost per feature.

IntermediateWhat is streaming, and when would you use it?

Streaming means the model sends the answer piece by piece as it's generated, instead of waiting for the full response. Technically, the API sends server-sent events, and I forward them from my backend to the browser.

I'd use it when a person is waiting and watching, like an author clicking "Suggest a blurb" or a support agent drafting a reply. The total time is the same, but seeing text appear after half a second feels much faster than a blank spinner for eight seconds.

I would not stream for background jobs or when I need structured JSON that I validate before saving. There I just wait for the full response. One thing to remember: with streaming, I still need to handle errors mid-stream and log the final token usage.

Interviewers look for: it improves perceived speed for interactive UI, and knowing when not to use it.

IntermediateExplain RAG in simple terms. How would you build a support bot over our FAQs?

RAG means Retrieval-Augmented Generation. In simple words: before asking the model a question, we first search our own documents for the relevant parts and give those to the model. So it answers from our policies, not from its memory.

For BookLeaf's support bot:

  • Collect FAQs, package details, royalty policy, shipping timelines for India and US.
  • Split them into small chunks and create embeddings. I'd store them in PostgreSQL with pgvector, since we'd already have Postgres.
  • When an author asks "How long does printing take?", find the top few matching chunks.
  • Send those chunks plus the question to the model, with an instruction to answer only from them and say "I'll connect you to the team" otherwise.

For order-specific questions, the bot should fetch the author's real order status from our database, not guess.

Interviewers look for: a plain explanation, a sensible store like pgvector, and a clear handoff to humans.

AdvancedHow would you measure whether the AI output is actually good?

"It looks fine to me" isn't enough, so I'd set up a simple evaluation process.

  • A test set: 30 to 50 real books with blurbs or categories the team already approved.
  • Automatic checks: valid JSON, word count, genre from our allowed list, no banned words.
  • Human scoring: the ops team rates a sample, maybe 1 to 5 for accuracy and tone.
  • Real-world signal: how often the team or author accepts the draft as-is versus heavily edits it. That's the best metric.

Every time I change the prompt or the model, I rerun the test set and compare before shipping. Some teams use another LLM as a judge, which is useful for scale, but I'd still check it against human ratings first.

Interviewers look for: a fixed test set, re-running on every change, and a business metric like acceptance rate.

IntermediateWhat does human-in-the-loop mean, and where would you use it?

It means the AI suggests, and a person decides. The AI does the first 80% of the work, and a human checks and approves before anything is final.

At BookLeaf, I'd use it for anything an author or reader sees, or anything with money or legal impact: blurbs, support replies, metadata going to Amazon or distribution partners, and anything touching royalties. Low-risk internal work, like tagging a support ticket, can be automatic, with someone spot-checking.

In the UI, this looks like a "Draft" status with Approve, Edit and Reject buttons, and I'd record who approved it. That gives us an audit trail, and the edits themselves become great data for improving the prompt later.

Interviewers look for: risk-based thinking about where humans are required, and a concrete UI and audit trail.

AdvancedAuthors trust us with unpublished manuscripts. How do you handle privacy when sending text to an AI?

This is a real concern, because a manuscript is the author's intellectual property before it's even published.

  • Send the minimum: for most tasks, the synopsis or a few pages is enough, not the whole book.
  • Check provider terms: OpenAI and Anthropic say API data isn't used for training by default, but there's still some retention for abuse monitoring. I'd check the current terms and whether zero-data-retention options apply.
  • Strip personal data: author phone numbers, addresses and bank details never go to the model.
  • Be transparent: mention AI processing in our terms, and ideally let authors opt out.
  • Logging: don't store full prompts with manuscript text in our logs forever.

Interviewers look for: data minimisation, knowing provider retention policies, and author consent. This shows you think about trust, not just features.

IntermediateOpenAI or Anthropic — how would you choose?

Honestly, both are very capable now, so I wouldn't pick based on hype. I'd decide based on our task.

  • Run the same 30 to 50 test cases on a model from each and compare quality, speed and cost.
  • Check features we need: structured outputs, tool calling, long context for manuscripts, batch pricing.
  • Check data and privacy terms, and rate limits for our volume.

Often Claude models do well on long documents and careful writing, and OpenAI has a very broad ecosystem. But that can change every few months, which is exactly why I'd put a thin wrapper in our code, like an aiClient.generate() function, so switching providers or using one as a fallback is a small change, not a rewrite.

Interviewers look for: testing on your own data instead of opinions, and not locking the codebase to one provider.

IntermediateWhat is tool calling (function calling)?

Tool calling lets the model ask our code to do something. I describe some functions to the model, with a name, a description and a JSON schema for the inputs. The model doesn't run anything itself. It replies saying "call getOrderStatus with order ID 4821". My backend runs that function, sends the result back, and the model uses it to write the final answer.

For BookLeaf, a support assistant could have tools like getOrderStatus, getRoyaltySummary or getBookStage. So when an author asks "Where's my book?", the answer comes from real data.

The safety part is important: my code still checks permissions, so the model can only fetch data for the logged-in author. And I'd start with read-only tools. Anything like issuing a refund needs a human.

Interviewers look for: the model requests, your code executes; permission checks stay in your code.

Personalise: You haven't shipped production LLM work yet, so build a small demo before the interview, for example a Node endpoint that turns a book synopsis into validated JSON metadata with structured outputs, or a tiny tool-calling bot. Then say "I built a small version of this last week" and describe it.

8. Automation — n8n, Make, Zapier

BasicWhat is n8n, and why do teams use it?

n8n is a workflow automation tool. You build workflows visually by connecting nodes: a trigger starts it, like a webhook or a schedule, and then each node does a step, like reading a Google Sheet, calling an API, sending an email or calling OpenAI. It also has a Code node for custom JavaScript or Python when needed.

Teams use it because they can connect tools quickly without building and deploying a full service. Compared to Zapier and Make, n8n can be self-hosted, which gives more control over data and cost, and it's more developer-friendly.

For a team like BookLeaf, with lots of repeated ops steps across many tools, it's a fast way to automate glue work, while the core business logic lives in proper code.

Interviewers look for: triggers and nodes, self-hosting as the key difference, and knowing it's for glue work.

Personalise: n8n isn't on your CV yet, so before the interview, run n8n locally with Docker and build one small workflow (webhook → OpenAI → Google Sheet → email). Then you can say "I set this up myself" honestly.

IntermediateWalk me through a workflow you'd build for a new book submission.

Something like this:

  • Trigger: a Webhook node receives the submission from the dashboard with the book ID.
  • Fetch: get the full details from our API: author, package, manuscript link.
  • Validate: check the manuscript file exists, the format is DOCX or PDF, and required fields like title and author name are filled. If not, email the author what's missing.
  • Branch by package: an IF or Switch node, since different packages need different tasks.
  • Create tasks: create tasks for editing, cover design and ISBN in our task tool or database.
  • Notify: email or WhatsApp the author "We've received your manuscript", and post in the team's Slack channel.

I'd make sure the book ID is used to avoid creating tasks twice, and attach an error workflow so failures alert someone.

Interviewers look for: a clear trigger, validation, branching, and thinking about duplicates and failures, not just the happy path.

BasicWhat kinds of triggers are there? When would you use each?
  • Webhook trigger: something happens and another system calls our URL instantly. Good for a new submission, a Razorpay payment, or a new Shopify order. It's real-time.
  • Schedule trigger: runs at fixed times, like a cron job. Good for a daily summary of books stuck in one stage, or a monthly royalty report.
  • App triggers: built-in nodes that watch a service, like a new row in Google Sheets or a new email. Some of these poll every few minutes.
  • Manual trigger: for testing or one-off runs.

I prefer webhooks when the other system supports them, because polling wastes runs and adds delay. One n8n detail: the Webhook node has a test URL and a production URL, and the production one only works after the workflow is activated.

Interviewers look for: knowing push (webhook) vs pull (schedule/polling) and picking the right one.

IntermediateHow do you handle errors and retries in n8n?

A few layers:

  • Retry on Fail: on nodes that call external APIs, I turn on Retry on Fail with a few tries and a wait between them. That handles temporary blips.
  • On Error setting: for steps that aren't critical, like a Slack message, I let the workflow continue instead of stopping everything.
  • Error workflow: I'd create one shared workflow starting with the Error Trigger node and set it as the error workflow in each workflow's settings. When anything fails, it sends the team the workflow name, the failed node, the error and a link to the execution.

And for important flows, like payment-related ones, I'd also have a daily check that compares what should have happened with what did, so silent failures get caught.

Interviewers look for: node-level retries, the Error Trigger workflow, and alerts that a human actually sees.

AdvancedWhat if the same event arrives twice? How do you prevent duplicates?

This happens a lot. Razorpay, Shopify and Stripe all say webhooks can be delivered more than once, and retries in our own workflow can repeat a step too. So workflows need to be idempotent, meaning running them twice gives the same result as running once.

How I'd do it:

  • Every event has a unique ID, like the payment ID or the webhook event ID.
  • Before doing work, check if that ID is already in a "processed events" table. If yes, stop.
  • In the database, put a unique constraint on that ID, so even if two runs race, only one insert succeeds.
  • Use "upsert" instead of "create" where possible.

Without this, an author could get two confirmation emails, or worse, a book could get two print orders.

Interviewers look for: the word idempotency, a unique event ID, and a database constraint as the real safety net.

IntermediateWhen would you use automation tools versus writing custom code?

My rough rule:

  • Automation tool when it's glue between existing tools, the logic is simple, it may change often, and ops people may want to see or tweak it. Like "new form entry → Sheet → Slack".
  • Custom code when it's core business logic, involves money, needs proper tests, has high volume, or has complex rules. Royalty calculation and payment handling, for example, belong in code with tests and version control.

A good middle ground is having n8n call our own API endpoints. n8n handles the trigger and the "who to notify" part, and the real logic stays in tested code. And if a workflow grows to 40 nodes with code blocks everywhere, that's a sign it should become a service.

Interviewers look for: a clear rule of thumb, not "always code" or "always no-code". Startups value people who use the fastest right tool.

IntermediateSelf-hosted n8n or n8n Cloud?

n8n Cloud is quick to start, with no servers to maintain, updates and backups are handled, but you pay per plan based on executions.

Self-hosted on our own VPS with Docker is cheaper at high volume and keeps author data on our servers, but now we own updates, backups, uptime and security. For a self-hosted setup I'd use Postgres instead of the default SQLite, put it behind Nginx with HTTPS, back up the database, and keep the encryption key that protects stored credentials safe. If volume grows, n8n has a queue mode with Redis and separate workers.

For BookLeaf, with high volume and an existing in-house setup, self-hosting probably makes sense, as long as someone clearly owns it. I'd check what's already in place first.

Interviewers look for: trade-off between convenience and control/cost, and knowing what self-hosting actually requires.

BasicHow do you handle credentials and secrets in automation tools?

Always use the tool's built-in credentials feature, never paste API keys directly into nodes or HTTP headers in plain text. In n8n, credentials are stored encrypted and nodes just reference them, so they don't appear in exported workflow JSON.

  • Give each integration its own key with the least access it needs.
  • Separate credentials for test and production.
  • Limit who can see and edit credentials in the tool.
  • For incoming webhooks, protect them: verify signatures from Razorpay or Shopify, or use a secret header, so random people can't trigger our workflows.
  • Rotate keys when someone leaves the team.

Interviewers look for: built-in credential storage, least privilege, and securing incoming webhooks too.

IntermediateHow do you monitor automations and find failed runs?

n8n keeps an executions log showing every run, its status, and the data at each node, so I can open a failed run and see exactly where it broke. I'd make sure failed executions are always saved.

But I don't want someone to have to check the log manually. So:

  • The error workflow sends an alert to a Slack channel or email immediately.
  • A daily summary: how many runs succeeded and failed per workflow.
  • A "heartbeat" check for scheduled workflows, so if the daily report didn't run at all, we notice.
  • Business checks, like "any paid order without a print task after two hours?"

Make and Zapier have similar run histories and email alerts.

Interviewers look for: using the executions log, proactive alerts, and catching workflows that silently didn't run.

IntermediateHow would you connect n8n to OpenAI?

n8n has built-in OpenAI nodes and AI nodes, so I'd add the OpenAI credential once and use those. If I need a feature the node doesn't expose, I can use the HTTP Request node to call the API directly.

Example: when a book is submitted, send the synopsis to OpenAI and ask for a draft blurb and keywords as JSON. Then a Code node or the structured output setting validates the JSON, and the result is saved as a draft in our database and the editor is notified.

Things I'd be careful about: turning on retries for rate limits, limiting how much text is sent, and adding an IF node to handle bad or empty responses. For anything complex, like RAG over our policies, I might do it in our backend and just call that from n8n.

Interviewers look for: built-in nodes vs HTTP Request, validating output, and handling rate limits.

IntermediateHow do you test and document workflows?

Testing: I run each node step by step in the editor using test data. n8n lets you pin sample data on a node, so I can test later steps without triggering the real webhook again. I'd test bad cases too: missing fields, a duplicate event, an API failure. And I'd keep a separate test workflow or environment pointing to sandbox credentials, like Razorpay test mode, so we never email real authors while testing.

Documentation:

  • Clear workflow and node names, like "Submission → Create Design Task".
  • Sticky notes inside the workflow explaining the why.
  • A simple shared doc listing every workflow: what triggers it, what it does, who owns it.
  • Export workflow JSON to Git as a backup and history.

Interviewers look for: pinned test data, sandbox credentials, and a workflow inventory so automations don't become a mystery.

BasicHow are Make and Zapier different from n8n?

All three connect apps with triggers and actions, but they fit different people.

  • Zapier: the easiest, huge number of app integrations, great for non-technical people. A "Zap" is mostly a linear flow. It gets expensive at high volume because you pay per task.
  • Make: a visual canvas of "scenarios" with modules, good for branching and data mapping, and usually cheaper than Zapier for complex flows. Billing is based on operations or credits.
  • n8n: the most developer-friendly, can be self-hosted, has code nodes and good AI nodes, and pricing is per workflow execution rather than per step.

At BookLeaf, I'd use whatever the team already uses well, and if we're doing high-volume work with author data, I'd lean towards self-hosted n8n.

Interviewers look for: a fair comparison on ease, cost model and control.

9. Bubble & the Migration to Code

BasicWhat is Bubble?

Bubble is a no-code platform for building full web apps. You design pages in a visual editor, and it gives you a built-in database and hosting.

  • Data types are like tables, and each record is called a "thing". So a "Book" data type with fields like title, author and status.
  • Workflows are the logic: "When the Submit button is clicked → create a new Book → send an email".
  • Privacy rules control who can see which data.
  • API Connector calls outside APIs, and backend workflows run on the server, can be scheduled, and can be exposed as API endpoints.
  • Plugins add extra features.

It's great for moving fast, which is probably why BookLeaf built ops on it.

Interviewers look for: you understand Bubble's concepts in developer terms, not that you look down on no-code.

IntermediateYou haven't worked in Bubble. How would you get productive quickly?

That's true, I haven't used Bubble in production. But the concepts map closely to what I do every day: data types are tables, workflows are event handlers, privacy rules are like the row-level security I built at Xellerate, and the API Connector is just calling REST APIs.

My plan for the first week or two:

  • Do Bubble's official manual and short tutorials, and build a tiny app myself.
  • Go through our app's data tab and draw the data model as a diagram.
  • List the main workflows and the API calls, and check the logs to see what's heavy.
  • Start with small, low-risk fixes with someone reviewing.

That diagram and list would also become the starting point for the migration plan.

Interviewers look for: honesty plus a concrete ramp-up plan and clear transferable skills.

Personalise: spend a weekend building a small Bubble app (e.g. a book submission form with a Book data type, a privacy rule and an API Connector call). Then you can say "I built a small app to learn it".

IntermediateWhat are Bubble privacy rules, and why do they matter?

Privacy rules are set on each data type and decide which users can see which records and fields, and whether they can find them in searches. They're enforced on Bubble's server.

They matter a lot, because a common Bubble mistake is only hiding things in the UI. If the privacy rule is missing, the data can still be pulled through the browser or the API. For BookLeaf, one author should never see another author's royalty statement, bank details or manuscript.

So I'd set a rule like "this Book is visible when Current User is the Book's author, or Current User's role is Admin". It's the same idea as the row-level security I set up at Xellerate across 10+ roles. One of the first things I'd do is audit the existing privacy rules.

Interviewers look for: knowing hiding in the UI is not security, and linking it to your RBAC experience.

IntermediateHow do the API Connector and backend workflows help connect Bubble with other systems?

They're the two directions of integration.

  • API Connector (Bubble → outside): lets Bubble call external APIs, like OpenAI, a print partner, or our new Node service. Keys can be marked private so they stay on the server.
  • Backend workflows (outside → Bubble): can be exposed as API endpoints, so Razorpay, n8n or our new services can call into Bubble. They can also run on a schedule or loop over lists in the background.
  • Data API: lets outside code read and write Bubble data directly.

These are exactly what make a gradual migration possible. New code can read from and write to Bubble during the transition, so we don't have to switch everything in one day.

Interviewers look for: both directions, and the link to migration.

IntermediateWhat are Bubble's limits? Why migrate at all?

Bubble is great for getting started, but at 1,200 books a month, some limits start to hurt:

  • Cost: Bubble charges based on workload units, so heavy searches and workflows can get expensive as volume grows.
  • Performance: large lists and complex searches can get slow, and we have limited control over queries and indexes.
  • Vendor lock-in: the app can't be exported as code. We depend on their pricing and their uptime.
  • Engineering practice: version control, code review, automated tests and complex logic are harder than in code.
  • Hiring: it's easier to hire and grow developers on a standard stack like Next.js and Postgres.

But I'd be careful: migration is a big cost too, so it should be driven by real pain points, not just "code is better".

Interviewers look for: specific limits (workload units, lock-in, testing) and a balanced view.

AdvancedHow would you plan the migration from Bubble to code?

I'd never do a big-bang rewrite. I'd use the strangler pattern: move one piece at a time while Bubble keeps running.

  • Map it: document data types, workflows and integrations, and find which parts cost the most workload units or cause the most pain.
  • Build the foundation: a Node API with Postgres, auth and CI/CD.
  • APIs first: move logic behind APIs. Bubble calls our API through the API Connector, so Bubble becomes more of a frontend over time.
  • One module at a time: pick something self-contained, like royalty reports or order tracking. Build it, run it in parallel, compare results, then switch.
  • Frontend last: rebuild the author dashboard in Next.js once the backend is stable.

Each step is small, shippable, and can be rolled back.

Interviewers look for: strangler pattern, Bubble staying live, and a clear order of what moves first and why.

AdvancedHow would you migrate the data safely?
  • Design the new schema properly: Bubble data is loosely structured, so I'd clean it into proper Postgres tables with foreign keys, and keep the Bubble unique ID as a column so every record can be traced back.
  • Export: use Bubble's Data API with pagination, or CSV exports, into a staging area.
  • Transform and clean: fix duplicates, bad emails, missing values, and log every record that didn't fit.
  • Verify: compare counts, and check totals like total royalties owed per author. Spot-check real records with the ops team.
  • Sync during transition: for the module being moved, keep both sides in sync through webhooks or backend workflows until we fully switch.
  • Rehearse: run the full migration on a copy first, more than once.

And of course, backups before every step.

Interviewers look for: keeping old IDs, validating with business totals, rehearsals and backups.

AdvancedWhat are the biggest risks of this migration, and how do you avoid downtime?

The biggest risks are losing or corrupting data, breaking a flow the ops team depends on daily, and the migration dragging on forever while new features stop.

How I'd reduce them:

  • Move small modules, with a feature flag to switch back to the Bubble version instantly.
  • Run old and new in parallel for a while and compare outputs, especially for money.
  • Do the final switch for each module at a low-traffic time, with a clear rollback plan.
  • Involve the ops team early. They know the edge cases that aren't written anywhere.
  • Keep shipping some business features during the migration, so the founders see value throughout.
  • Write tests for the new code before switching, especially royalty and payment logic.

Interviewers look for: feature flags, parallel runs, rollback plans, and involving the actual users.

IntermediateHow would you keep improving the Bubble dashboard while planning to replace it?

The business can't stop for a migration, so Bubble needs to stay healthy.

  • Fix bugs and handle urgent requests in Bubble, since that's what the team uses every day.
  • Optimise expensive searches and workflows to cut workload units. That saves money right now.
  • For any new feature, ask "will this be thrown away soon?" If it's complex, build the logic as an API in code and call it from Bubble. Then it carries over to the new system.
  • Don't add more complexity to parts that are about to move.

So every change either helps today or moves us closer to the new system, ideally both.

Interviewers look for: respect for the current tool, plus building new logic in a way that survives the migration.

IntermediateHow would you explain the migration plan to the founders?

I'd keep it about business outcomes, not technology. Something like:

"Right now, Bubble costs us X per month, and that grows with every book. Some pages are slow for the ops team, and we can't easily test changes, so bugs reach authors. The plan is to move one part at a time, starting with royalty reports, which is our most expensive and most error-prone area. Bubble keeps running the whole time, so nothing breaks for authors. Each step takes a few weeks, and we can stop or reverse any step."

Then I'd show a simple timeline, the cost of each phase, and what we gain: lower monthly cost, faster pages, and fewer mistakes. I'd also be honest that some months will have fewer new features.

Interviewers look for: plain language, costs and benefits in rupees and time, and honest trade-offs. This role works directly with founders.

Part 4 — Integrations, DevOps & Design

10. Payments, Shopify & Print-on-Demand

IntermediateWalk me through a Razorpay payment flow, end to end.

Say an author buys a publishing package for ₹14,999.

  • Create order on the server: my backend looks up the price from the database, never from the frontend, and calls Razorpay's Orders API with the amount in paise (1499900), currency INR and our internal receipt ID. I save the order as "created".
  • Checkout: the frontend opens Razorpay Checkout with the order_id and our public key ID.
  • Callback: on success, Checkout returns razorpay_payment_id, razorpay_order_id and razorpay_signature. The frontend sends these to my backend.
  • Verify: the backend checks the signature. Only then is it marked paid.
  • Webhook: Razorpay also sends a webhook like payment.captured or order.paid, which is the final confirmation.

Then we start the publishing workflow and send the author a receipt.

Interviewers look for: server-side order creation, amount in paise, signature verification, and the webhook as the source of truth.

Personalise: Razorpay isn't on your CV yet, so build a small Node demo in Razorpay test mode before the interview (create order → checkout → verify signature → webhook). Then say "I built this in test mode to understand it".

IntermediateHow do you verify a Razorpay payment signature?

Razorpay signs the result with our key secret, so we can prove the payment details weren't faked. On the server, I build the string order_id + "|" + payment_id, using the order ID from my database, create an HMAC SHA256 of it with the key secret, and compare it to the signature I got.

const expected = crypto
  .createHmac("sha256", process.env.RAZORPAY_KEY_SECRET)
  .update(`${order.razorpayOrderId}|${paymentId}`)
  .digest("hex");
const ok = crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));

For webhooks it's similar but different: Razorpay sends an X-Razorpay-Signature header, which is an HMAC SHA256 of the raw request body using the webhook secret. So I must verify against the raw body, before JSON parsing changes it.

Interviewers look for: the exact order_id|payment_id format, server-side secret, raw body for webhooks, and a safe comparison.

IntermediateWhy not just trust the frontend success callback?

Two reasons.

Security: the frontend is controlled by the user. Anyone can call our "payment success" endpoint with fake data. That's why we verify the signature on the server.

Reliability: even for honest users, the callback can just never arrive. The payment succeeds, but the author closes the tab, their internet drops, or the bank redirect fails. If we only rely on the callback, we have money taken but no order in our system, and an angry author calling support.

Webhooks fix this, because Razorpay calls our server directly and retries if we don't respond. So I treat the frontend callback as a nice fast update for the UI, and the verified webhook as the source of truth. Both paths call the same idempotent "mark order paid" function.

Interviewers look for: both reasons, security and reliability, and one idempotent handler for both paths.

AdvancedHow do you handle failed and duplicate payments?

Failed payments: the order stays "created" or "failed" and I listen for payment.failed. The author sees a clear "Payment didn't go through, try again" message, and retrying reuses the same order. If money was debited but the payment isn't captured, Razorpay auto-refunds it, but I'd still show a helpful message so the author doesn't panic.

Duplicates:

  • Webhooks can arrive more than once, so I store the event ID or payment ID with a unique constraint and skip ones already processed.
  • The "mark as paid" update only runs if the order isn't already paid, inside a transaction.
  • If an author really pays twice for the same order, a daily check flags it and we refund the second payment.
  • Disable the Pay button after the first click.

Interviewers look for: idempotency with unique constraints, state checks, and a process for real double payments.

IntermediateHow would you handle refunds?

Refunds go through Razorpay's Refunds API using the payment ID, either full or partial, for example if an author cancels before editing starts and we keep a small fee.

  • Only admins can trigger refunds, and I log who did it and why.
  • Check the refund amount isn't more than what's left to refund.
  • Store a refund record with status "pending", and update it when the refund.processed or refund.failed webhook arrives.
  • Update the order and stop any work in progress, like the print job.
  • Email the author with the expected timeline, since bank refunds can take several working days.

The refund policy itself, how much and when, is a business decision. I'd make sure the code follows it consistently.

Interviewers look for: permissions, audit trail, webhook-driven status, and side effects on the order.

IntermediateHow would you handle US authors with Stripe and multiple currencies?

I'd use Stripe for US payments, probably Stripe Checkout, because it's quick, hosted and handles cards and 3D Secure for us. Under the hood it uses PaymentIntents.

  • The backend creates a Checkout Session with the price in cents and USD, and our order ID in metadata.
  • Confirm through webhooks like checkout.session.completed, verified with the endpoint's signing secret against the raw body.
  • Use idempotency keys when creating payments.

For currencies, I'd always store integers in the smallest unit plus a currency code, never floats. Prices per region are set in our database, not converted live. For royalty reports, I'd record the exchange rate used at the time of each transaction. And I'd put Razorpay and Stripe behind one common payment interface, so the rest of the code doesn't care which gateway was used.

Interviewers look for: webhooks with signing secret, integer amounts with currency, and a gateway abstraction.

IntermediateHow would you integrate Shopify for book sales?

If BookLeaf sells authors' books through a Shopify store, I'd connect it like this:

  • Products: when a book is published, create or update the Shopify product through the Admin API (GraphQL is now the main one): title, cover, price, ISBN as SKU.
  • Orders: subscribe to webhooks like orders/create and orders/paid. Verify the X-Shopify-Hmac-Sha256 header against the raw body.
  • Respond fast: Shopify expects a quick 200 response, so I save the event and process it in a background job.
  • Dedupe using the webhook ID, since Shopify can resend.
  • Royalties: link each order line to our book ID, so author royalties are calculated from real sales.
  • Fulfilment: when we ship, update fulfilment with the tracking number so the customer gets notified.

Interviewers look for: Admin API, verified webhooks, quick acknowledgement with async processing, and mapping sales to royalties.

AdvancedDesign the print-on-demand order flow.

I'd model each order as a clear state machine, so everyone can see where every book is:

PAID → PRINT_QUEUED → PRINTING → PRINTED → PACKED → SHIPPED → DELIVERED (plus ON_HOLD and CANCELLED)

  • Paid: payment confirmed by webhook. Check the print-ready PDF and cover are approved.
  • Print queue: group jobs by book size and paper type, since BookLeaf prints in-house in Delhi. For US orders, send to a US print partner's API instead.
  • Warehouse: scan a barcode when printed and packed, which updates the status.
  • Shipping: create the shipment with the courier API, save the AWB or tracking number.
  • Tracking: courier webhooks or polling update status, and the author and buyer get notified.

Every status change is logged with time and who did it, so we can see where orders get stuck.

Interviewers look for: a state machine, India vs US routing, and visibility into delays.

AdvancedHow would you integrate a print or distribution partner's API?

I'd treat any third-party API as unreliable and wrap it carefully.

  • Read the docs and sandbox first: file specs for PDFs and covers, auth, rate limits, webhooks.
  • Adapter layer: one module, like printPartner.createJob(), so if we change partners, only that file changes.
  • Queue the calls: send jobs from a background worker with retries and backoff, never in the user's request.
  • Store their IDs: save the partner's job ID with our order, and use our order ID as a reference so retries don't create duplicate print jobs.
  • Status updates: use their webhooks if available, otherwise poll on a schedule.
  • Logging: log requests and responses, without secrets, for debugging disputes.

This is the same pattern I used for integrations at my previous jobs: background jobs, retries and clean adapters.

Interviewers look for: adapter pattern, queues, idempotent job creation, and logging.

AdvancedHow would you reconcile payments with orders?

Reconciliation means checking that money received and orders in our system match exactly. Even with webhooks, things slip through.

I'd run a daily job:

  • Pull yesterday's payments from Razorpay and Stripe through their APIs.
  • Match each one to an order by order ID.
  • Flag three cases: paid but no order (webhook missed, so fix it), order marked paid but no payment (a bug, investigate), and amount mismatch.
  • Also match settlements, the money actually reaching the bank, with gateway fees, for the finance team.

The output is a simple report or Slack message for ops, with zero mismatches on a good day. This matters a lot for royalties too, since author payouts depend on correct sales numbers.

Interviewers look for: a scheduled job, the three mismatch types, and tying it to finance and royalties.

11. DevOps & Deployment

BasicTell me about the CI/CD pipeline you've set up.

At RDX Digital Solutions, I set up a CI/CD pipeline with GitHub Actions that deploys our client apps to AWS.

  • On every pull request: install, lint, type-check, and run tests with Jest or Vitest. If anything fails, the PR can't be merged.
  • On merge to main: build the app, build a Docker image, and deploy to the server.
  • Secrets are stored in GitHub Actions secrets, not in the repo.
  • After deploying, a simple health check confirms the app is up.

The biggest benefit was confidence. Before, deploys were manual and someone was always nervous. After, deploying became a boring, repeatable thing we could do several times a day. For a "bias for shipping" team like BookLeaf, that's exactly what you want.

Interviewers look for: a real pipeline you built, what runs on PR vs merge, and the impact on shipping speed.

Personalise: add real details from RDX: which AWS service, how long a deploy takes, and any bug the pipeline caught.

BasicWhat is Docker, and why use it?

Docker packages an app with everything it needs, the Node version, libraries and config, into an image. A running image is a container. It runs the same way on my laptop, in CI and on the server.

Why it helps:

  • No more "works on my machine". A new junior can run the whole stack with docker compose up.
  • Easy to run several services on one VPS: the API, a worker, Redis, maybe n8n.
  • Rollbacks are simple: just run the previous image tag.

I'd use a multi-stage Dockerfile to keep images small, not run as root, and never bake secrets into the image. Those come from environment variables at runtime.

Interviewers look for: consistency across environments, onboarding, and basic best practices.

IntermediateHow would you deploy a Node app to a VPS?
  • Server setup: a small Ubuntu VPS, SSH keys only, firewall allowing just ports 22, 80 and 443, and automatic security updates.
  • Run the app: either Docker Compose, or PM2 to keep Node running and restart it if it crashes or the server reboots.
  • Nginx in front: as a reverse proxy to the app's port, handling gzip, upload size limits for manuscripts, and serving static files.
  • SSL: free certificates from Let's Encrypt with Certbot, set to auto-renew.
  • Deploy: GitHub Actions SSHes in, pulls the new image, and restarts.

The database I'd keep on a managed service if the budget allows, because backups and updates are handled. If not, on its own server with daily backups.

Interviewers look for: security basics, a process manager, Nginx reverse proxy and SSL. This is a bonus skill in the JD.

BasicHow do you manage environment variables and secrets?

Config that changes between environments, like database URLs, Razorpay keys and OpenAI keys, goes in environment variables, never in code.

  • A .env file locally, which is in .gitignore, plus a .env.example with dummy values so everyone knows what's needed.
  • In CI, GitHub Actions secrets. On the server, env files with strict permissions, or AWS Secrets Manager or Parameter Store.
  • Validate env variables at startup with Zod. If a key is missing, the app fails immediately with a clear error instead of breaking later.
  • Separate keys for dev, staging and production, especially test vs live for Razorpay.
  • Rotate secrets if leaked or when someone leaves.

In Next.js, I'm careful that only NEXT_PUBLIC_ variables go to the browser.

Interviewers look for: no secrets in Git, validation at startup, separate keys per environment.

AdvancedHow do you deploy without downtime?

The idea is to start the new version before stopping the old one.

  • PM2: cluster mode with pm2 reload restarts instances one by one.
  • Docker: start the new container, wait for its health check to pass, switch Nginx to it, then stop the old one. That's basically blue-green.
  • Graceful shutdown: on SIGTERM, stop taking new requests and finish the current ones, so an author's upload doesn't get cut off.

The tricky part is the database. Migrations must be backward-compatible, so old and new code both work during the switch. For example, to rename a column: add the new column, write to both, backfill, switch reads, and only drop the old column in a later deploy.

Interviewers look for: health checks, graceful shutdown, and especially backward-compatible migrations.

IntermediateHow would you set up monitoring, logging and alerts?

For a small team, I'd keep it simple but cover the basics:

  • Structured logs: JSON logs with a library like Pino, including a request ID, user ID and order ID, so I can follow one problem across services.
  • Error tracking: Sentry or similar, so we see errors with stack traces before authors report them.
  • Uptime checks: a service like UptimeRobot or Better Stack pinging the health endpoint.
  • Business alerts: these matter most. "No new submissions in 6 hours", "payment webhooks failing", "print queue stuck".
  • Server metrics: CPU, memory and disk, with an alert before the disk fills up with manuscript uploads.

Alerts go to one Slack channel, and I'd keep them few so people don't start ignoring them.

Interviewers look for: errors, uptime and business-level alerts, without alert fatigue.

IntermediateHow do you handle database backups and restore?

A backup only counts if you've tested restoring it.

  • Automated daily backups with pg_dump, or a managed database's automatic backups with point-in-time recovery.
  • Store them elsewhere: in S3, in a different region or account from the server, with encryption, and a retention like 30 days.
  • Files too: manuscripts and covers in S3 with versioning turned on, so an accidental delete or overwrite can be undone.
  • Test restores: once a month, restore into a test database and check the data. Write down how long it took.
  • Before risky changes: take a manual backup before big migrations.

For BookLeaf, losing royalty data or an author's final manuscript would be really serious, so this isn't optional.

Interviewers look for: offsite storage, file versioning, and actually testing restores.

IntermediateA deploy broke production. What do you do?

First, fix it for users, then find the cause.

  • Roll back right away: redeploy the previous Docker image tag or Git commit. Since every deploy is tagged, this takes a couple of minutes. Or turn off the feature flag if the change was behind one.
  • Communicate: tell the team and founders in one line what's broken and that we're rolling back.
  • Check the damage: did bad data get written? Did any payments or emails go out wrongly?
  • Find the cause calmly, with logs and Sentry.
  • Prevent it: add a test for that case, and write a short no-blame note on what happened.

One catch: if a database migration ran, rolling back the code isn't enough. That's why I keep migrations backward-compatible.

Interviewers look for: rollback first, clear communication, and learning without blame.

IntermediateHow would you keep infrastructure costs low for a startup?
  • Start simple: one or two well-sized VPS machines with Docker Compose, not Kubernetes. Scale when the numbers say so.
  • Right-size: check actual CPU and memory use, and downsize idle servers.
  • Storage: move old manuscripts and print files to cheaper S3 storage classes with lifecycle rules.
  • CDN and images: serve covers through a CDN as compressed WebP. At RDX, image optimisation and lazy loading gave us a 94% load improvement, and that also cuts bandwidth cost.
  • Watch SaaS bills: Bubble workload units, Zapier tasks and AI tokens can grow quietly. Track them monthly.
  • Budget alerts on AWS and AI providers.

I'd also share a simple monthly cost summary with the founders, so cost is visible, not a surprise.

Interviewers look for: pragmatic choices, avoiding over-engineering, and watching SaaS and AI spend too.

12. System Design for BookLeaf

AdvancedDesign the author dashboard.

First I'd ask what authors actually come for: "Where is my book?", "What do I need to do?", and "How much have I earned?".

  • Home: each book with a progress tracker (Manuscript → Editing → Cover → ISBN → Printing → Live) and a clear "Action needed" box, like "Approve your cover".
  • Book page: upload manuscript, review proofs and covers, comment threads with the team.
  • Orders and royalties: sales by channel, royalty statements, payout history.

Tech: Next.js with TanStack Query, a Node API, PostgreSQL, S3 for files, and role-based access so authors only see their own books while staff see everything. Data is scoped by author ID in every query. And it must work well on mobile, since many authors in India will open it on their phone.

Interviewers look for: starting from user needs, clear screens, access control and mobile-first thinking.

AdvancedDesign the book submission to publishing pipeline for 1,200 books a month.

1,200 a month is about 40 books a day, so the challenge isn't raw scale, it's tracking and coordinating many steps and people.

  • Book state machine: SUBMITTED → EDITING → AUTHOR_REVIEW → TYPESETTING → COVER → ISBN → PRINT_READY → PUBLISHED. Only allowed transitions, each logged.
  • Tasks: each stage creates tasks assigned to the right team member, with due dates.
  • Events and jobs: each stage change emits an event. Background workers (a queue like BullMQ on Redis) handle emails, AI checks, file processing and partner API calls.
  • Ops board: a view per stage showing counts, ageing and overdue books, so bottlenecks are visible.
  • SLAs: alert if a book sits in a stage too long.

This gives founders a clear view: how many books are in each stage, and where they're getting stuck.

Interviewers look for: realising it's a workflow problem, a state machine, background jobs, and visibility for ops.

IntermediateHow would you store large manuscripts and cover files?

Files go in object storage like S3, never in the database. The database just stores metadata: file key, size, type, version and who uploaded it.

  • Direct uploads: the backend gives a pre-signed upload URL, and the browser uploads straight to S3. Big files don't pass through our server. Multipart upload for very large files.
  • Private by default: downloads use short-lived signed URLs. I built exactly this at Smile Returns for private healthcare files.
  • Versions: every new manuscript or cover is a new version, never overwritten, so we can go back to "v3 that the author approved".
  • Validation: check file type and size, and scan for viruses in a background job.
  • Organise: paths like books/{bookId}/manuscript/v3.docx.

Interviewers look for: object storage, pre-signed URLs, private access, and versioning.

IntermediateHow would you design notifications to authors over email and WhatsApp?
  • One notification service: the rest of the code just says "send COVER_READY to author 123". The service picks channels and templates.
  • Queue it: sending happens in background jobs with retries, so a slow email provider never slows down the app.
  • Channels: email through a provider like SES or Postmark. WhatsApp through the WhatsApp Business API with pre-approved message templates, which is very effective in India.
  • Preferences: authors can choose channels, and important ones like payment receipts always go by email.
  • Log everything: what was sent, when, and delivery status, so support can answer "I never got the email".
  • No spam: idempotency keys so the same event never triggers two messages, and grouping small updates.

Interviewers look for: a central service, async sending, WhatsApp templates, logs and deduplication.

AdvancedHow would you design royalty calculation and reporting?

Royalties are money and author trust, so accuracy and traceability matter more than speed.

  • Sales ledger: every sale is one row, with channel (our store, Amazon, Flipkart, Shopify), book, quantity, price, currency, date, and source reference. Rows are never edited, only corrected with adjustment rows.
  • Royalty rules: stored per book or per package, with effective dates, since rates can differ by channel.
  • Monthly job: calculates royalties per book per author and saves a statement showing exactly which sales it includes.
  • Money: integers in paise or cents, exchange rate saved per sale.
  • Review step: finance approves before payouts go out.
  • Author view: statement and sales breakdown in the dashboard, downloadable as PDF.

And lots of unit tests for edge cases: returns, refunds, rate changes mid-month.

Interviewers look for: an append-only ledger, versioned rules, reproducible statements, and tests.

IntermediateHow would you design order tracking across India and the US?
  • One shipment model: order ID, region, carrier, tracking number, status, and a history of events. The same model works for both countries.
  • Carrier adapters: one adapter per courier, Indian aggregators or couriers here and US carriers or a print partner there, all converting their statuses into our common ones: SHIPPED, IN_TRANSIT, OUT_FOR_DELIVERY, DELIVERED, RETURNED.
  • Updates: courier webhooks where available, otherwise a scheduled job polls active shipments.
  • Customer view: a tracking page and notifications at key steps.
  • Ops alerts: flag shipments with no update for several days.

Store all times in UTC and show them in the user's time zone, IST or US time.

Interviewers look for: a common status model with adapters, webhooks plus polling, and time zones.

AdvancedA third-party API is down. How do you keep the system reliable?

I assume every external API will fail sometimes, whether that's payments, couriers, the print partner or OpenAI.

  • Don't call them in the user's request when you don't need to. Save the work as a job, and the user sees "Processing".
  • Retries with backoff, and after too many failures, move the job to a dead-letter queue and alert someone.
  • Timeouts on every call.
  • Circuit breaker: if an API keeps failing, stop calling it for a few minutes instead of piling up requests.
  • Fallbacks: a second courier, or manual handling by ops.
  • Catch up later: reconciliation jobs fix anything missed while it was down.

So for example, if the courier API is down, books still get packed, and labels are created automatically once it's back.

Interviewers look for: async jobs, retries, timeouts, circuit breakers and reconciliation.

AdvancedHow would the system scale as BookLeaf grows?

Honestly, 1,200 books a month is not a heavy load for a well-built Node and Postgres app. I'd scale based on real measurements, not guesses.

  • Database first: proper indexes and no N+1 queries. At Xellerate, composite indexes and fixing N+1 queries made our APIs 35% faster without any new servers.
  • Stateless API: so we can add more instances behind Nginx or a load balancer.
  • Background workers scale separately from the API.
  • Caching with Redis for things read often, like book catalogue pages.
  • CDN for covers and static files.
  • Later, read replicas for reports and analytics.

The bigger growth risk is usually operational, more people and steps, not traffic. So clean workflows and visibility matter as much as servers.

Interviewers look for: right-sized thinking, measuring first, and a real example of optimisation.

For a small team, I'd choose boring, popular tools that the team can hire for and get help with: Next.js, Node with TypeScript, PostgreSQL, Prisma, Redis, Docker. That stack also covers what the JD asks for.

When deciding on any new tool, I'd ask:

  • Does it solve a real problem we have now?
  • Can the juniors learn and maintain it?
  • Is it well maintained with a good community?
  • What's the cost, and how hard is it to leave later?

I'd write each big decision as a short note: the options, what we chose and why. Then six months later, nobody wonders "why did we pick this?". And I'd prefer one language, TypeScript, across frontend and backend so everyone can work on everything.

Interviewers look for: pragmatism over hype, team skills, and documented decisions.
